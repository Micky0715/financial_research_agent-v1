## 0. 一分钟摘要

这一轮做了四件事，每件事都推翻或修正了之前的一个结论：

| 做了什么 | 之前的说法 | 现在的说法 |
|---|---|---|
| 单变量消融 | "Harness 让成功率 +12.5pp" | **归因错了**。那是 checkpoint **一个功能**的收益，其余四项能力实测影响为 **0** |
| 回归集重建 | "41 条回归集" | 31 条 bad case 逐条分类，只有 **13 条**能变成可执行任务，其余写明不能用的理由 |
| 恢复指标重建 | "Recovery Success Rate = 0" | 那个指标**在数学上不可能非 0**。换成 7 个指标后实测同工具重试恢复 **0.6875** |
| 真实链路 Canary | "离线 Number Grounding = 0.9956" | 真实环境是 **0.8126**；14 条完成的真实运行里 **12 条**含无源数字 |

**三句话总结：**

1. **Harness 没有让这个系统更常成功，而是让失败变得可解释。**
   回归集上两臂成功率完全相同（0.8462），差别是"说不清为什么失败"的比例从 **0.5385 → 0**。
2. **指标接近满分，通常说明评测和被测对象共享了同一个假设**，而不是说明系统好。
3. **能相减的前提是分母相同。** 现在报告脚本会在分母不一致时**拒绝出结论**，而且这个拒绝行为本身有测试。

## 1. 先补五个概念（小白必读）

如果你没做过 Agent 评测，先花三分钟看懂这五个词。后面所有内容都建立在它们之上。

### 1.1 什么是"口径"？

**口径 = 这个数字到底是怎么算出来的。**

举个生活里的例子：两家公司都说"员工平均月薪 2 万"。
A 公司算的是税前、含年终奖摊薄、只统计正式员工；
B 公司算的是税后、不含奖金、含实习生。
两个"2 万"不能比较——**不是数字错了，是口径不同**。

在评测里同样：
"成功率 80%"必须说清楚——多少个任务？跑几次算一次成功？
用哪套评分规则？失败了算 0 分还是"不适用"？

**本轮一半以上的工作就是在修口径**，而不是在改代码逻辑。

### 1.2 什么是 fixture（离线夹具）？

Agent 要上网搜资料。但如果每次测试都真的上网：

- 网页内容天天变 → 今天 80 分明天 70 分，你分不清是代码退步了还是网页改了；
- 慢（一次几分钟）、花钱（调模型 API）；
- 断网就跑不了测试。

所以做**离线 fixture**：预先准备好一批"假网页""假搜索结果",
测试时把真实的网络调用替换成读这些文件。这样测试**确定性**、免费、断网可跑。

**代价**（本轮的核心发现）：假网页是**你自己造的**。
你造它的时候心里想着"报告需要引用哪些数字"，于是就把那些数字写进了假网页。
结果就是——**报告引用什么，页面里就有什么，数字溯源率自然接近 100%**。
这不是系统好，是你和自己对答案。

### 1.3 什么是"消融实验"（Ablation）？

**消融 = 一次只拆掉一个零件，看整体差多少。**

你说"我的车跑得快是因为换了引擎、轮胎和空气动力套件"。
面试官会问："那到底是哪个起作用？"

正确做法：造 4 个版本——全都装（参照）、只拆引擎、只拆轮胎、只拆套件。
哪个版本变慢了，就是哪个零件有用。

**关键要求：一次只能拆一个。** 如果你同时拆掉引擎和轮胎，
变慢了你也不知道该怪谁。这正是旧 README 犯的错。

### 1.4 什么是 Canary（金丝雀）？

矿工下井带一只金丝雀——它对瓦斯敏感，它先出事，人就撤。

在工程里，**Canary = 用真实环境、真实花钱、小批量地跑一次**，
目的不是拿统计结论（样本太小），而是**看看真实世界里会冒出什么离线测不出来的东西**。

本轮 canary 只跑了 16 条、花了 $0.2520，但它直接挖出了
两类离线永远造不出来的错误，和一个被 fixture 系统性掩盖的质量问题。

### 1.5 什么是"反向验证"（这是本轮的方法论核心）

**写完一个测试，把它保护的代码故意改坏，确认测试会变红。**

为什么必须做？因为**一条永远绿的测试和没有测试是一样的**。

真实例子（本轮）：我写了"消融矩阵必须在 Grader 集合不一致时拒绝出结论"的测试。
为了证明它不是摆设，我把那个检查改成 `if False:`，
重跑——对应测试立刻变红；改回来——重新变绿。
**这条测试是真的在守东西。**

本轮所有关键守卫都做了反向验证，下文会逐个标出。

## 2. 本轮的起点：一句话说清问题

上一轮结束时，项目的状态是：

> **功能完整，测试全绿，报告漂亮——但所有数字都是自己和自己对答案。**

具体表现为四个症状：

| 症状 | 表现 | 为什么危险 |
|---|---|---|
| 对照无效 | README 的 +12.5pp 同时动了两个变量 | 面试一问"哪个变量起作用"就答不上来 |
| 数据虚假 | 41 条"回归集"里大量是**历史 Bug 的标题**被当成研究问题 | 跑通了也不代表回归被防住 |
| 指标失效 | Recovery Success Rate 长期显示 0 | 没人追问为什么是 0 |
| 全靠 fixture | token 与费用**结构性为 0** | 任何成本/时延结论都没有依据 |

本轮目标：**把这四条逐个变成有证据、可复现、口径明确的结论——哪怕结论是"没有收益"。**

## 3. 改动一：把一张无效对照表换成单变量消融

### 3.1 旧表错在哪（三个独立的致命伤）

README 原来有一张表，结论是"Harness 让 Task Success 从 0.6818 提升到 0.8068，+12.5pp"。

这张表**三个问题各自独立成立**，任意一个都足以让结论作废：

**问题一：一次关掉了多个变量。**
baseline 臂同时关掉了预算门禁**和** checkpoint。就算差异真实存在，
也无法知道该归功于哪一个。

**问题二：两臂的 Grader 集合不同。**
baseline 的结果文件是用**旧的、已证明退化的** tool grader 打的分，
harness 臂是用修好的 grader 打的分。评分规则都不一样，减法没有意义。
（这就是 1.1 节说的"口径不同"。）

**问题三：0.6818 这个数字本身是一次已修复回归的产物。**
它是我自己引入的一个 bug 留下的：去重命中时返回了精简投影、丢掉了正文，
导致 BrowserAgent 拿不到 `content` 而丢弃全部来源。

更要命的是，把差异**逐任务拆开**后发现：
差异**恰好集中在 11 个任务上，且全部是 `interrupt_after_browse` 场景**——
对照臂关掉了 checkpoint，却被要求从中断处恢复，直接抛异常。

**这不是"成功率提升"，这是"有没有这个能力"。**

### 3.2 重做的方式

现在是 7 个臂，除 legacy 外每个臂与参照臂 `harness_full` **只差一个布尔开关**：

| 臂 | 与参照臂的唯一差异 |
|---|---|
| `legacy_no_harness` | 完全不绑定 Harness（参照点，不是单变量臂） |
| `harness_full` | **参照臂**：全部能力开启 |
| `abl_no_retry` | 只关重试 |
| `abl_no_checkpoint` | 只关 checkpoint |
| `abl_no_budget` | 只关预算门禁 |
| `abl_no_context_mgmt` | 只关上下文压缩 |
| `no_fallback` | 只关权威站点 fallback 轮 |

有两个设计决定值得单独说：

**（1）`baseline_v4` 被故意排除在消融集之外。**
`evals/runners/arms.py::ablation_arms()` 不包含它，因为它捆绑了两个变化。
留着它就会诱使下一个人重新犯问题一。

**（2）报告脚本会拒绝出结论。**
`scripts/build_ablation_matrix.py::validate()` 在打印任何数字之前检查三件事：

```
1. 各臂任务数一致吗？
2. 各臂 trial 数一致吗？
3. 各臂 Grader 集合一致吗？
```

任意一项不过，报告顶部直接印：

> ⚠️ **对照有效性检查未通过，以下数字不可作为归因结论**

这个"拒绝"行为本身有 **16 条测试**（`tests/harness/test_ablation_validity.py`），
并且**反向验证过**：把 Grader 集合检查改成 `if False:`，对应测试立刻失败。

### 3.3 dev 集（88 任务 × 1 trial）实测结果

| 指标 | legacy | **harness_full** | 只关重试 | 只关 checkpoint | 只关预算 | 只关上下文 | 只关 fallback |
|---|---:|---:|---:|---:|---:|---:|---:|
| Task Success | 0.7500 | **0.8068** | 0.8068 | **0.6818** | 0.8068 | 0.8068 | 0.8068 |
| Unresolved Failure | n/a | **0** | 0 | **0.1250** | 0 | 0 | 0 |
| Citation Coverage | 0.8568 | 0.7318 | 0.7318 | 0.6935 | 0.7318 | 0.7318 | 0.7318 |
| 平均工具调用数 | n/a | 13.59 | 13.28 | 11.78 | 13.59 | 13.59 | **9.99** |

> **为什么 legacy 是 `n/a` 而不是 0？**
> legacy 没有 trace，事件派生指标**不存在**。写 0 会读成"legacy 的虚假成功率是 0"，
> 看起来比 harness 还好。`n/a` 表示**缺失能力**，不是**缺失分数**。
> 这一条也有测试守着。

**怎么读这张表（这是最重要的部分）：**

**① 只有 checkpoint 一个能力影响成功率。**
关掉它成功率掉 12.5pp（0.8068 → 0.6818），同时 Unresolved Failure 从 0 升到 0.125。

所以旧结论的 **数字恰好是对的，归因是错的**——那是 checkpoint 一个功能的收益，
不是整层 Harness 的收益。这是我最愿意在面试里主动讲的一段。

**② retry / budget / 上下文压缩 / fallback 对成功率的影响是精确的 0。**
不是"影响很小"，是这四个臂的成功率与参照臂**完全相同**（都是 0.8068）。

诚实的解释：离线 fixture 里注入的故障类型，不需要这些能力就能通过。
这**不能**证明这些能力无用，只能证明**当前评测集证明不了它们有用**。
如果我说"retry 提升了稳定性"，我手上没有证据。

**③ fallback 在当前 fixture 数据集上是纯成本**（仅限本数据集，未在真实环境验证）。
关掉它，工具调用从 13.59 降到 9.99（少 3.6 次），
而成功率、来源数、引用覆盖率**全部不变**。
它要么该被优化掉，要么需要一个能证明其价值的场景（比如权威站点限流）。

**④ legacy 的 Citation Coverage 反而更高（0.8568 vs 0.7318）——这一条我没藏。**
已确认的中间事实：legacy 平均拿到 3.47 个来源，harness 2.97 个，来源多则锚点多。
但**为什么 harness 拿到的来源更少，没有查清**（最可能是执行器去重与早停的交互）。

文档里它被标为**未解决项，不是已解释项**。
在查清之前把它说成"Harness 的取舍"，就是**把未知包装成设计意图**。

### 3.4 重构回归集（13 任务）的结果 —— 本轮最重要的一句话

| 指标 | legacy | harness |
|---|---:|---:|
| Task Success | 0.8462 | 0.8462 |
| **Unresolved Failure** | **0.5385** | **0** |
| 有结构化 Trace | 否 | 是 |

两臂成功率**完全相同**。差别全在第二行：

> ## **Harness 没有让这个系统更常成功，而是让失败变得可解释。**

legacy 有 53.85% 的任务以"说不清为什么没成"结束；Harness 是 0——
每个失败都带错误分类、停止原因和 trace 事件。

## 4. 改动二：回归集从"缺陷标题"变成"可执行任务"

### 4.1 原来的问题

原本有 41 条"回归数据"。打开一看，大量条目长这样：

```
query: "Planner 输出重复任务导致执行链路不稳定"
```

这是**历史 Bug 的标题**，不是一个研究请求。
把它丢给一个金融研报 Agent，它会认真地去研究"什么是执行链路不稳定"。
**跑通了也不代表那个 Bug 不会再犯。**

### 4.2 重构方式：31 条逐条分类，一条都不静默丢弃

| 类别 | 条数 | 含义 |
|---|---:|---|
| `deterministic` | **13** | 已重构为可执行任务：真实 query + 故障注入 fixture + 明确期望 |
| `not_agent_behaviour` | 9 | 真实缺陷，但属于开发工具或性能问题，不是 agent 行为回归 |
| `needs_network` | 5 | 只能在真实 provider / TLS / 子进程下复现 |
| `needs_human_review` | 4 | 期望值必须由人设定（会计口径、行业判断） |

**每一条 `not_agent_behaviour` 都写了具体理由**，而不是"不适用"。
这很重要：面试官会问"你是不是把跑不过的都删了？"——
答案是每条都有归档理由，可逐条核对（`evals/datasets/regression_manifest.json`）。

一个 `deterministic` 任务长这样（不再是 Bug 标题）：

```python
"subject":          "某新能源公司",
"query":            "……投资价值分析",
"fixture_scenario": "alias_only_sources",   # 故障注入：来源只含别名
"expected_outcome": "……",
"required_tools":   [...],
"forbidden_tools":  [...],
"forbidden_claims": [...],
"note":             "对应 Bad Case 3：别名来源被误判为无关"
```

为此在 `evals/runners/replay.py` 新增了 4 个故障注入场景
（别名来源、单一可用来源、单域名灌水、高精度小数），现共 20 个场景。

### 4.3 诚实的限制

**13 条任务的 `gold_status` 全部是 `needs_human_review`——没有任何一条被人工确认过。**

它能防住"这个缺陷再次发生"，但**不能声称"期望值本身是正确的"**。
这需要人工标注闭环真正跑完（当前 `human_verified = 0`）。

## 5. 改动三：恢复指标从 1 个变成 7 个，并发现旧指标**结构性恒为 0**

这是本轮技术含量最高的一段，也是最能扛追问的一段。

### 5.1 现象

旧的 `recovery_success_rate` 长期显示 **0**。
按字面意思读："这个系统从来没有从失败中恢复过。"

但 Harness 明明有重试、有 fallback、有 checkpoint 恢复。哪个是错的？

### 5.2 根因：这个指标在数学上不可能非 0

旧 grader 的算法（`evals/graders/deterministic.py::RecoveryGrader`）：

```python
failed_steps    = {发出过 tool_call_failed 的 step_id}
completed_steps = {发出过 tool_call_completed 的 step_id}
recovery_rate   = len(failed_steps & completed_steps) / len(failed_steps)
```

看起来很合理："某个步骤失败过，后来又成功了 → 恢复成功"。

**但去看执行器实际怎么发事件：**

`TOOL_CALL_FAILED` 只在 `ToolExecutor._finish_failure()` 里发出，
而这个函数**只有在重试循环彻底放弃之后**才会被调用
（`src/tools/executor.py`，重试成功的分支直接 `return` 成功结果）。

也就是说：

- 一个**恢复成功**的步骤：只发 `TOOL_CALL_COMPLETED`，**从不发** `TOOL_CALL_FAILED`；
- 一个**最终失败**的步骤：发 `TOOL_CALL_FAILED`，**不会**再发 completed。

**两个集合按构造互斥，交集恒为空集。**
这个指标不是"太粗糙"，是**对任何可能的 trace 都等于 0**。

### 5.3 用真实数据验证这个推断

推断完还必须验证。在 88 个任务的真实 trace 上统计：

```
有失败的运行        : 21/88
失败过的 step      : 67    ← 旧指标的分母
被重试过的 step    : 27    ← 新指标的分母
旧指标分子（失败∩完成）: 0     → 0.0000
新指标分子（重试∩完成）: 22    → 0.8148   <- micro（按 step 池化，非报告里的 macro 0.6875）
```

**恢复一直在发生（22/27），旧指标只是看不见。**

顺带看到失败但**从未被重试**的步骤的错误类型：
`AUTH_ERROR: 55`、`NOT_FOUND: 6`、`UNKNOWN: 1`——
这些是不可重试的永久错误，它们只能把旧指标往 0 拽。

### 5.4 为什么之前没人发现？两个原因，第二个更值得讲

**原因一：它的 `passed` 判据里有一条后门。**

```python
return self.result(rate, rate > 0 or run.status in ("succeeded", "degraded"), ...)
                         # ↑ 指标是 0，但只要运行成功了就判「通过」
```

于是**指标永远是 0，判定永远是"通过"**，没人会去看一个一直通过的项。

**原因二（关键）：它的单元测试手写了一条执行器发不出来的 trace。**

```python
result = RecoveryGrader().grade(task(), artifacts(events=[
    {"event_type": "tool_call_failed",    "step_id": "s1"},
    {"event_type": "tool_call_completed", "step_id": "s1"},   # ← 同一个 s1
    {"event_type": "tool_call_failed",    "step_id": "s2"},
]))
assert result.metrics["recovery_success_rate"] == 0.5
```

同一个 `step_id` 既发 failed 又发 completed——**真实执行器根本不会产生这种序列**。

于是形成了一个完美的假象：
**测试是绿的，grader 的算术是对的，而指标在生产里毫无测量能力。**

> 这是本轮最重要的方法论教训：
> **一条测试只证明"代码对它的输入做了正确的事"，
> 不证明"那个输入在现实中会出现"。**

### 5.5 怎么修的

**没有删掉那条旧断言**（它对它的输入而言是正确的），而是：

1. 在 `RecoveryGrader` 的 docstring 里写清它为什么恒为 0，附上 67/27/0/0.8148 这组实测数据；
2. 新增一条**由真实执行器驱动**的测试：脚本化一次 transient 失败，让真实重试路径去恢复，
   断言 `tool_call_failed` **根本没有出现**在事件流里，且旧指标看不见、新指标看得见；
3. 报告里把它的标签改成 `~~Recovery Success Rate~~（已废弃，见下方七项恢复指标）`。

### 5.6 替换它的 7 个指标

| 指标 | 回答什么问题 | dev 实测 |
|---|---|---:|
| `same_tool_retry_recovery` | 同工具退避重试救回来了吗 | **0.6875** <sup>†</sup> |
| `cross_tool_fallback_recovery` | 换一个工具救回来了吗 | **0.4762** |
| `degraded_completion` | 降级了但仍然完成了吗 | — |
| `checkpoint_resume_success` | 断点恢复的运行最终成功了吗 | **1.0** |
| `false_success` | **声称成功但结构上无效** | **0.0114** |
| `success_with_ungrounded_numbers` | 完成了但数字没出处 | 0.0154 |
| `unresolved_failure` | 失败了且没有任何解释 | **0** |

<sup>†</sup> **分母提示**：`0.6875` 是 **macro** —— 48 个至少调度过一次重试的 run，取其逐 run 比率的均值；本文 5.3 节的 `0.8148` 是 **micro** —— 81 个被重试的 step 中 66 个恢复。两者同源但**聚合层级不同，不可互换引用**。

**每个指标只对应一种恢复机制**，所以哪个掉了就知道该查哪里——
这是旧的单一指标做不到的。

**为什么 `false_success` 要拆成两个？**
它原本同时在两件事上触发：报告"结构无效"（零来源、悬空引用、注入内容泄漏）
和报告"数字没出处"。但 v4 已经把 `report_compliance_pass_rate = 0.0` 记录为**预期行为**，
把质量问题混进完整性指标会让它**不可行动**——你看到它涨了，不知道是系统在撒谎还是文风变了。

现在 `false_success` 只管**完整性**（必须恒为 0），
数字溯源交给 `success_with_ungrounded_numbers`。这个拆分也做了反向验证。

## 6. 改动四：第一次花钱跑真实链路

### 6.1 为什么必须花这个钱

在此之前，项目里**每一个数字都来自离线 fixture**。
离线模式用 stub 替换了 `BaseAgent.call_llm`，所以 token 和费用**结构性地等于 0**——
不是测得很小，是**根本没有测**。

面试里这会被一句话问穿：

> "你说这套 Harness 控制了预算，那一次运行多少钱？"

答不出具体数字，整个预算门禁的叙事就是空的。

### 6.2 怎么做的（不是简单地"跑一遍"）

`evals/runners/live_canary.py`，16 个人工分层挑选的真实主体：

- 覆盖 4 类任务（公司 / 行业 / 宏观 / 结构化取数）+ 4 个专门的边界场景；
- `--yes` 必填，`--max-cost-usd` 是**硬上限**，超限立刻停；
- 每条跑完**立即落盘**，中途被杀不会丢已花的钱；
- 结果**永不与 fixture 结果合并**——报告脚本只读 `live_canary.jsonl`。

> **为什么"不合并"这么重要？**
> 把离线成功率和真实成功率平均一下，得到的数字**两者都不描述**。
> 这是评测里最常见的自欺方式之一。

### 6.3 实测结果（16/16 全部跑完，共 $0.2520）

| 指标 | 实测值 |
|---|---:|
| 平均单次费用 | **$0.0158** |
| 平均输入 / 输出 Token | 11,270 / 4,342 |
| 平均时延 | 179.94s |
| **P95 时延** | **340.92s** |
| 平均工具调用数 | 20.0 |
| Task Success（符合预期终态） | 0.9375 |
| False Success | **0** |
| Unresolved Failure | **0** |

终态分布：succeeded 13 / degraded 1 / insufficient 2。

**两条 insufficient 是设计上应该失败的：**

- 一条虚构主体（希兹维恩量子玄武科技）被实体校验拦下 → `entity_unverified`；
- 一条首轮所有来源都不可用 → `no_usable_sources`。

**一条 degraded** 是预算降级阶梯在真实环境真的触发了
（真实错误分布里 `BUDGET_EXCEEDED` 出现 18 次尝试）。

> 这三条比 13 条成功更有说服力：**安全机制在真实环境里真的开火了**，
> 而不只是在 fixture 里被构造出来。

### 6.4 最重要的发现：fixture 系统性高估了数字溯源质量

| 指标 | 离线 dev（88×3） | 真实 canary（16×1） |
|---|---:|---:|
| Number Grounding | 0.9956 | **0.8126** |
| 成功但含无源数字 | 0.0154 | **0.8571** |

翻译成人话：

- 离线看：1000 个数字里只有 **4 个**找不到出处；
- 真实环境：1000 个数字里有 **187 个**找不到出处；
- **14 条完成的真实运行里，12 条至少含一个无源数字。**

**原因不是模型变差了**，而是 fixture 的构造方式决定了这个指标测不出问题
（回看 1.2 节）：fixture 网页里的数字是**按报告需要生成的**，
所以报告引用什么、页面里就有什么。

真实网页的数字散落在图表、PDF、被 HTML 清洗掉的表格里，
模型于是写出"同比增长约 12%"这种**在正文里找不到锚点**的句子。

> ### 方法论结论
> **一个指标在 fixture 上接近满分，往往说明 fixture 和被测对象共享了同一个假设，
> 而不是说明系统好。**
>
> 上一轮的 Tool F1 = 1.0（空期望分支导致的假满分，真实对抗集 **0.4616**）
> 是同一个病的另一种表现。

### 6.5 Canary 直接暴露的一个真实代码缺陷

真实运行产生了 32 次失败的工具调用，其中 **8 次是 `UNKNOWN`**（占 1/4）。

UNKNOWN 按不可重试处理，所以**行为是对的，但归因是错的**——
运维看到 UNKNOWN 只能去翻日志。查下来是两类：

1. **`empty_content_after_cleaning`**：网页取回成功（HTTP 200），
   但 HTML 清洗后没有正文（以及扫描版 PDF 的 "no text layer"）。
   对这个 URL 而言是**永久失败**——重试不可能凭空造出文字。
2. **`468 Client Error`**：反爬前端自己编的**非标准状态码**，没有任何规则认领。

补两条规则进 `src/runtime/errors.py` 后，**8 次 UNKNOWN 全部归入 `PERMANENT_FAILURE`，
其余 24 次分类一个都没有变**（无遮蔽）。

通用 4xx 规则被**刻意放在规则表最末尾**，因为 429（限流）和 408（超时）
也是 4xx 但**可重试**，401/403/404 有各自的类。测试逐条守住这些不被抢：

```
429 Client Error → RATE_LIMIT          ✓ 未被抢
408 Client Error → TIMEOUT             ✓ 未被抢
404 Client Error → NOT_FOUND           ✓ 未被抢
403 Client Error → AUTH_ERROR          ✓ 未被抢
468 Client Error → PERMANENT_FAILURE   ✓ 新规则生效
"read 4096 bytes then failed" → UNKNOWN ✓ 不误伤普通消息
```

### 6.6 一个不能作弊的细节：规则改在 canary 之后

这两条规则是在 canary **已经跑起来之后**才改的，运行中的进程加载的是旧模块。

于是有三个选择：

| 选项 | 为什么不选 |
|---|---|
| 重跑一次 canary | 要再花钱，且第二次的网络状况不同，不可比 |
| 改写已有 trace 里的分类 | **重写历史证据不可接受**，这是红线 |
| ✅ 离线重放 | trace 里**逐字保存了真实错误消息**，用当前规则重放同一批消息 |

做法是 `scripts/replay_canary_error_classes.py`。
报告第 4.2 节并列两列 + Δ：

| 错误类型 | 运行时记录 | 按当前规则重放 | Δ |
|---|---:|---:|---:|
| `NOT_FOUND` | 8 | 8 | 0 |
| `PERMANENT_FAILURE` | — | 8 | **+8** |
| `UNKNOWN` | 8 | — | **−8** |
| `TRANSIENT_NETWORK` | 7 | 7 | 0 |
| `TIMEOUT` | 6 | 6 | 0 |
| `AUTH_ERROR` | 3 | 3 | 0 |

**两列合计均为 32。**

这个脚本的附带价值：以后任何分类规则改动，都能在**真实数据**上零成本验证，
而不是在自己编的 fixture 上验证。

## 7. 本轮修出的五个真实缺陷

按"是否我自己造成的"分组，因为面试官很吃这一套——
**主动交代自己犯的错，比罗列别人的错可信得多。**

### 7.1 别人（或历史代码）的三个

| # | 缺陷 | 影响 | 怎么发现的 |
|---|---|---|---|
| 1 | 旧 Recovery 指标**结构性恒为 0** | 恢复能力长期不可测量 | 追问"为什么一直是 0" |
| 2 | `empty_content` / `468` 被误判为 UNKNOWN | 1/4 的真实失败无法归因 | **真实 canary**，fixture 造不出来 |
| 3 | 结果文件**谎报自己的配置** | 见下 | 读 dev 重跑输出时起疑 |

**第 3 个值得展开。** 离线 eval 会关掉共享搜索缓存以保证确定性
（共享缓存会让一次运行依赖于"之前跑过什么"，这是离线基准的大忌），
跑完在 `finally` 里恢复。但 `environment` 块是在**恢复之后**才写的：

```python
# run_one_trial: 关缓存 → 跑 → finally: 恢复缓存
# run_suite:     ... 然后才写 environment
"search_cache": config.ENABLE_SEARCH_CACHE   # ← 读到的是「已恢复」的值 True
```

于是结果里写着 `search_cache: true`——
**一个干净的运行，主动声称自己被共享缓存污染过。**

修成记录**实际生效值**，并加了一条**行为测试**（真跑一条离线任务，
断言 summary 报 False 而环境变量确实已恢复成 True）。反向验证：
改回读 ambient 值，测试立刻红。

### 7.2 我自己在这一轮里造成的两个

**缺陷 4：我把两个不同分母的数字放进了同一张对比表。**

上面 6.6 那张表的第一版，左列取自 `live_metrics.by_error`（按**尝试**计，含重试），
右列取自 trace 事件（按**失败的调用**计）。于是 `TRANSIENT_NETWORK` 显示成 **10 vs 5**——
看起来像"规则改动导致临时网络错误减半"，实际是**纯粹的分母不同造成的假差异**。

修法：两列都从同一批 trace 事件派生，合计都是 32。
并且在生成时加了断言 `sum(recorded) == sum(replayed)`，另有测试守着。

> 这件事我特意写进报告里，因为它**恰好就是我这一轮在批判的错误**（口径不同不能相减）。
> 犯它说明：**这类错误不是靠"小心一点"能避免的，必须靠机制（断言 + 测试）挡住。**

**缺陷 5：`docs/_evidence/result_hashes.json` 早就和磁盘不一致。**

报告里引用 sha256 是为了让读者能验证"这些数字是从当前这个文件算出来的"。
但这个哈希文件是我早先用一次性脚本生成的，后来重跑过 split 却没更新——
检查发现 **4 条已经过期**（其中 3 条是我这轮根本没碰的文件）。

> **过期的哈希比没有哈希更糟，因为它长得像证据。**

修法：写 `scripts/hash_results.py`（`--check` 只校验不重写），
并加一条守卫测试——**文档里出现的每一个 sha256，都必须对应某个当前文件的真实哈希**。

## 8. 三层追问演练

下面每题都按"第一层问事实 → 第二层问机制 → 第三层问漏洞"来准备。

### Q1：你说 Harness 有用，具体提升了多少成功率？

**第一层｜** 在重构回归集上是 **0**——legacy 和 harness 的 Task Success 都是 0.8462。
在 dev 集上是 +5.68pp（0.75 → 0.8068），但这**几乎全部**来自 checkpoint 一个能力。

**第二层｜那它的价值在哪？** 在可归因性。同一批任务上，
legacy 有 **53.85%** 的失败"说不清原因"，Harness 是 **0**。
生产里，能说出"是 provider 限流"还是"是参数错了"的系统，
和只能说"失败了"的系统，运维成本差一个数量级。

**第三层｜这个 0 是不是你把 grader 放宽了？**
不是，且这一点**不靠我的承诺，靠机制**：
两臂用同一份任务、同一份 fixture、同一个 Grader 集合，
`validate()` 在三项任一不一致时**拒绝出表**（退出码 1）。
`Unresolved Failure` 由 trace 事件派生；legacy 没有 trace，
所以它的其他事件派生指标全部标 `n/a`——
唯独这一项能算，因为"没有任何错误分类信息"本身就是它的观测结果。

### Q2：+12.5pp 那个数字是假的吗？

**第一层｜** 数字是真的，**归因是假的**。

**第二层｜** 三个独立问题：同时关了两个变量；两臂 Grader 集合不同（口径不可比）；
0.6818 本身是一次已修复回归的产物。

**第三层｜你怎么知道它是 checkpoint 而不是预算？**
逐任务拆开后，差异**恰好落在 11 个任务上，且全部是 `interrupt_after_browse` 场景**——
对照臂关掉 checkpoint 却被要求恢复，直接抛异常。
单变量消融进一步确认：只关预算的臂成功率与参照臂**完全相同**。

### Q3：retry 没有收益，那你为什么还留着它？

**第一层｜** 消融显示它对成功率的影响是**精确的 0**。

**第二层｜** 这不证明它无用，只证明**当前评测集证明不了它有用**——
离线 fixture 注入的故障类型不需要重试就能通过。
而真实 canary 里同工具重试恢复率是 **0.5**（n=10），说明它在真实环境确实在工作。

**第三层｜那你为什么不把它也在 fixture 里测出来？**
这正是待办：需要注入"第一次超时、第二次成功"这类**时序性**故障。
当前 20 个 replay 场景里没有这一类，所以我**不能**声称 retry 有离线证据。
我宁可留一个"未证明"，也不愿意补一个刚好能让它得分的场景——
那会变成为指标定制评测。

### Q4：Recovery Success Rate 一直是 0，你怎么才发现？

**第一层｜** 我去追问"为什么一直是 0"，而不是接受它。

**第二层｜** 根因是执行器只在**重试彻底放弃后**才发 `TOOL_CALL_FAILED`，
恢复成功的步骤只发 `COMPLETED`，两个集合按构造互斥，交集恒为空。

**第三层｜你怎么证明这不是你的猜测？**
两条证据：
(a) 88 个任务的真实 trace 统计——67 个失败 step、27 个被重试 step、
旧指标分子 **0**，新指标 22/27 = **0.8148**；
(b) 一条**由真实执行器驱动**的测试：脚本化一次 transient 失败让真实重试路径恢复，
断言 `tool_call_failed` 根本没有出现。
如果执行器以后改了这个行为，这条测试会失败并提示"应重新审视，而不是删除"。

### Q5：那为什么它的单元测试是绿的？

**第一层｜** 因为它手写了一条 `step_id` 同时发 failed 和 completed 的事件流。

**第二层｜** 真实执行器**发不出**这种序列。测试证明的是
"代码对这个输入做了正确的事"，不证明"这个输入在现实中会出现"。
再加上它的 `passed` 判据里有 `or run.status in ("succeeded","degraded")` 的后门，
所以**指标永远 0、判定永远通过**，没人会去看。

**第三层｜你有没有把这条测试删掉来让自己好看？**
没有。它对它的输入是正确的，删掉等于销毁证据。
我的做法是**新增**一条真实执行器驱动的测试，
并在 grader 的 docstring 里写清它为什么恒为 0（附实测数据）。
原则是：**不修改测试来迎合实现**——除非那条测试断言的是缺陷本身
（上一轮的 Tool F1 就是这种情况，我重写了它并写明理由）。

### Q6：16 条 canary 能说明什么？

**第一层｜** 能说明真实链路跑得通、单次约 $0.0158、P95 约 341s、
以及真实环境会出现哪些错误类型。

**第二层｜不能说明什么？** 不能作为成功率的统计结论——
**n=16、每条 1 trial、无置信区间**；不能当作线上指标——单机串行、无并发、
P95 不是 SLO；不能外推成本——主体热度决定检索轮数。

**第三层｜那你花这个钱值得吗？**
值得，而且回报是具体的：它挖出了 1/4 的真实失败被误判为 UNKNOWN，
以及 fixture 把 Number Grounding 从真实的 0.8126 高估成 0.9956。
**这两件事离线永远发现不了**——因为离线的错误类型和网页内容都是我自己造的。

### Q7：数字溯源率真实只有 0.81，这不是说明系统很差吗？

**第一层｜** 说明**报告质量有真实缺口**：14 条完成的运行里 12 条含至少一个无源数字。

**第二层｜** 但要区分两件事：
`false_success`（声称成功但结构无效）在真实环境是 **0**——
系统没有在"零来源"或"悬空引用"的情况下宣称成功。
无源数字属于**质量**问题，不是**完整性**问题。
这正是我把 `false_success` 拆成两个指标的原因——混在一起会让指标不可行动。

**第三层｜你打算怎么修？**
先别急着修。当前所有期望值都是 `needs_human_review`，
在没有人工 Gold 之前去优化这个指标，很可能是在优化我自己的推断。
正确顺序是：人工标注闭环 → 确认口径 → 再谈优化。

### Q8：你怎么保证报告里的数字来自现在这份结果文件？

**第一层｜** 每个结果文件都记 sha256 + 行数（`docs/_evidence/result_hashes.json`）。

**第二层｜** 但我发现这个文件本身会过期——检查时有 **4 条**已经和磁盘不一致。
**过期的哈希比没有哈希更糟，因为它长得像证据。**

**第三层｜那你现在怎么防？**
`scripts/hash_results.py --check` 可以只校验不重写（过期则退出码 1），
外加一条守卫测试：**文档里出现的每个 sha256 都必须对应某个当前文件的真实哈希**。
有人重跑了 split 却忘了更新文档，测试会红。

### Q9：你这一轮自己有没有犯错？

有两个，都写进了报告和代码注释：

1. **把两个不同分母的数字放进同一张对比表**（按尝试计 vs 按失败调用计），
   造成 `TRANSIENT_NETWORK 10 vs 5` 的假差异。讽刺的是，
   这**正是我这一轮在批判的错误**。修法不是"以后小心点"，
   而是加断言 `sum(recorded) == sum(replayed)` + 测试。
2. **`recovery.py` 的 docstring 写着"六个指标"，实际有七个**——
   是我把 `false_success` 拆成两个之后忘了改计数。写这份报告时核对发现并修正。

> 我把这两条留在报告里，是因为它们说明一件事：
> **这类错误不能靠自律避免，只能靠机制挡住。**

### Q10：所有测试都是离线的，会不会掩盖问题？

**第一层｜** 391 条测试可在**硬断网**下通过（`pytest -p audit_netblock_plugin`），
这是 CI 稳定性的优点。

**第二层｜** 也确实意味着测试覆盖不到真实网页漂移、限流、反爬。
本轮的 canary 就是专门补这个缺口的——并且**立刻**就补出了两类分类缺陷。

**第三层｜为什么不干脆把 canary 加进 CI？**
因为它花钱、慢（2880 秒）、且结果依赖当天网络，会让 CI 变成不稳定信号。
正确定位是**人工触发的验收步骤**，而不是门禁。
CI 里跑的是离线 391 条；canary 的结果单独成文、单独存哈希、**永不与离线结果合并**。

## 9. 仍然不能声称的

这一节比前面所有结论都重要。**面试里主动讲限制，通常比回避更加分。**

| 不能说 | 为什么 |
|---|---|
| "真实成功率是 X%" | n=16、每条 1 trial，无置信区间 |
| "真实时延**降低**了" / "成本**节省**了" | 只有一次真实测量，**没有改造前的真实基线**。可以说"真实成本是多少"，不能说"降低了多少" |
| "人工 Gold 数据集" | `human_verified = 0`，审核队列已就绪但无人填写 |
| "已通过完整回归门禁" | v004/v005 五个候选状态全是 `proposed`，门禁未跑 |
| "记忆显著提升效果" | A/B 规模不足（3 主体 × 2 会话，成功率全 1.0），按既定标准**默认关闭** |
| "生产级 / 高并发 / 高可用" | 单机 fixture，无压测、无 SLO、无线上流量 |
| "多智能体协作" | `normalize_plan` 把任何计划压成固定 5 阶段；对抗集实测 F1 = 0.4616，系统执行固定工具链 |
| Docker 部署已验证 | 未执行 build |

**还有一个明确的未解决项：**
legacy 的 Citation Coverage 比 harness 高（0.8568 vs 0.7318），
已确认中间事实是来源数不同（3.47 vs 2.97），但**根因未定位**。
在查清之前不能说成"Harness 的取舍"——**那是把未知包装成设计意图**。

## 11. 一页总结

**这一轮没写新功能，只做了一件事：把"看起来不错的数字"逐个拆开验证。**

结果推翻了自己之前的一个主要结论，并发现 5 个真实缺陷（其中 2 个是我这轮造成的）。

**最终能站住的三句话：**

> **1. Harness 没有让这个系统更常成功，而是让失败变得可解释。**
> 回归集上两臂 Task Success 完全相同（0.8462），
> 差别是 Unresolved Failure 从 **0.5385 降到 0**。
>
> **2. 指标接近满分，通常说明评测和被测对象共享了同一个假设。**
> 旧 Tool F1 = 1.0 来自空期望分支；离线 Number Grounding = 0.9956
> 来自"fixture 网页按报告需要生成数字"。
> 对应实测值分别是 **0.4616**（离线**对抗 fixture 集**，31 任务×3 trial，
> `gold_status` 全为 `synthetic_adversarial`，**不是真实线上 Tool F1**）
> 和 **0.8126**（真实 canary，n=16×1 trial）。两者环境不同，不可并列比较。
>
> **3. 能相减的前提是分母相同。**
> 旧 README 的 +12.5pp 同时改了两个变量、还换了 Grader 集合；
> 真实 Δ 属于 checkpoint 一个能力。
> 现在报告脚本会在三项一致性检查不通过时**拒绝给出归因结论**，
> 而且这个拒绝行为本身有测试，并做过反向验证。

**为什么这套东西适合面试：**

它展示的不是"我会用什么框架"，而是四种更稀缺的能力——

1. **能识别自己的结论为什么不可信**，并主动推翻它；
2. **能把"有用"拆成可归因的单变量结论**，哪怕结论是"没有收益"；
3. **能分清"测不出来"和"没有问题"**——前者要补评测，后者才是好消息；
4. **能把诚实写进机制**：拒绝出结论的脚本、守住分母的断言、
   校验哈希过期的测试——**而不是写进承诺里**。
